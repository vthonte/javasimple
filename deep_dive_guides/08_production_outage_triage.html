Production Troubleshooting & Live Incident War Room (4-7 Years On-Call Bar)

Step-by-step diagnostic workflows for the 3 most terrifying production outages: 100% CPU Spikes, Deadlocks / Connection Pool Depletion, and Heap OutOfMemoryErrors.

1 Outage 1: 100% CPU Spike on Linux / Kubernetes Pods

The Scenario: You receive a PagerDuty alert at 2 AM. Pod CPU is pinned at 100%, health checks are timing out, and response latency went from 30ms to 15,000ms.
The 4-Step Terminal Triage Command Sequence:
Step 1: Find the exact high-CPU OS Thread ID top -H -p <JVM_PID>

Displays individual threads. Suppose thread ID 28419 is consuming 98% CPU.

Step 2: Convert the Thread ID from decimal to hexadecimal printf '%x\n' 28419 # Outputs: 6f03

The JVM thread dump records thread native IDs (nid) in hex format.

Step 3: Take a thread dump snapshot jstack -l <JVM_PID> > threaddump.txt
Step 4: Grep for the hex thread ID in the dump grep -A 25 "nid=0x6f03" threaddump.txt

Instantly reveals the exact Java class and line number causing the spin (e.g. at com.example.service.ReportGenerator.parseData(ReportGenerator.java:142) - usually a runaway while loop or catastrophic regex backtracking!).

2 Outage 2: Connection Pool Exhaustion (HikariPool Connection Timeout)

The Error in Logs: HikariPool-1 - Connection is not available, request timed out after 30000ms.
Root Cause #1: Long Third-Party HTTP Calls inside @Transactional
@Transactional // DB connection checked out here!
public void processCheckout(Order order) {
    orderRepo.save(order); // takes 2ms
    
    // DISASTER: 3rd-party network call holding DB connection open!
    stripeClient.chargeCard(order.getAmount()); // takes 5,000ms!
}

If 10 requests hit checkout, all 10 HikariCP database connections are blocked for 5 seconds doing nothing but waiting for Stripe's network. Every other endpoint in your app starves and crashes!

Fix: Never make external API calls inside a database transaction. Execute the Stripe charge first, and open the @Transactional scope only for the 3ms required to write to PostgreSQL.

3 Outage 3: Thread Deadlocks (The Mutual Lock Freeze)

Thread 1 holds Lock A and waits for Lock B. Thread 2 holds Lock B and waits for Lock A. Both freeze forever.

How jstack Detects Deadlocks Automatically:

Run jstack -l <PID>. Scroll to the very bottom of the output. The JVM automatically runs cycle-detection algorithms and prints: 

Found 1 deadlock.
================
"pool-1-thread-1":
  waiting to lock monitor 0x00007f (object A),
  which is held by "pool-1-thread-2"
"pool-1-thread-2":
  waiting to lock monitor 0x00008b (object B),
  which is held by "pool-1-thread-1"
