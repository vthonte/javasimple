JVM Memory Management, Garbage Collection Algorithms & Production Memory Leaks

How the JVM allocates RAM, differences between Stack and Heap, how modern GCs (G1, ZGC) collect unreachable objects without freezing your servers, and how to debug OutOfMemoryError.

💡

ELI5: The Desk vs. The Warehouse (Stack vs Heap)

Beginner Mental Model
1. The Stack (Your Desk)

Every thread has its own desk. When a method starts, papers are placed on top. When the method finishes, the entire stack of papers is tossed into the trash instantly. Super fast, private to each thread, but tiny (~1MB).

2. The Heap (The Big Warehouse)

Shared by all threads. When you type new Order(), a big box is stored in the warehouse. Your desk only holds a shipping label (pointer) with the box ID. Large (gigabytes), but requires cleaning.

3. The Garbage Collector (The Janitor)

Walks through the warehouse. If a box has no shipping label pointing to it from any desk, the Janitor crushes it and recycles the space. Zero manual free() required!

1 The 3 Major JVM Memory Regions

In Node.js, V8 manages memory with an old-space and new-space heap (usually capped around 1.4GBâ€“2GB by --max-old-space-size). The JVM divides process memory into three distinct architectural zones:

Thread Stack Per-Thread

Allocated private for every active thread. Holds primitive values (e.g. int x = 5) and reference pointers to heap objects.

Lifecycle: Ultra-fast LIFO. Freed automatically when a method exits. Never touched by Garbage Collector!
Crash Failure: StackOverflowError (e.g. infinite recursion).
Heap Memory Shared

The largest region, shared across all threads. Every instance created with new User() or Spring Singleton lives here.

Lifecycle: Managed completely by the Garbage Collector (Young and Old Generations).
Crash Failure: OutOfMemoryError: Java heap space.
Metaspace Native RAM

Stores class bytecodes, method metadata, static variables, and reflection references.

Lifecycle: Lives in native OS memory (outside Heap). Introduced in Java 8 to replace PermGen.
Crash Failure: OutOfMemoryError: Metaspace.

2 How JVM Garbage Collection (GC) Works: Generational Hypothesis

The JVM's GC relies on the Weak Generational Hypothesis: *"Most objects die shortly after creation (e.g. temporary DTOs, HTTP request strings, loop variables)."*

The Journey of a Java Object through the Heap Generations:
1. Eden Space (Young Gen)

Every newly allocated object begins in Eden. When Eden fills up, a fast Minor GC fires. 98% of objects are immediately destroyed.

2. Survivor Spaces (S0 / S1)

Objects that survive Eden are copied to Survivor space. An "age" counter increments every time they survive a Minor GC cycle.

3. Old / Tenured Generation

When an object's age reaches the threshold (default: 15 cycles), it is promoted to the Old Gen. Spring Singletons and DB pools live here permanently.

Modern GC Collectors You Must Know in Senior Interviews:
  • G1GC (Garbage-First GC): The default since Java 9. Divides heap into thousands of equal regions. Prioritizes collecting regions containing the most garbage to meet target pause-time goals (e.g. -XX:MaxGCPauseMillis=200).
  • ZGC (Z Garbage Collector): Ultra-low-latency collector in modern Java 21. Performs all heavy GC work concurrently without stopping application threads. Guarantees pause times below 1 millisecond even on terabyte-sized heaps!

3 How Memory Leaks Actually Happen in Java (and How to Triage Them)

*"Wait, Java has garbage collection! How can it leak memory?"*
A memory leak in Java occurs when an object is no longer needed by your business logic, but an active reference path from a GC Root still exists, preventing the GC from ever freeing it.

Leak 1: Unbounded Static Collections (The In-Memory Cache Trap)
@Service
public class UserService {
    // STATIC collection stays alive for the ENTIRE lifetime of the JVM process!
    private static final Map<String, UserDTO> userCache = new HashMap<>();

    public void cacheUser(UserDTO user) {
        userCache.put(user.getId(), user); // Never expires or evicts!
        // Over months of uptime, this grows until Heap exhausts!
    }
}
Senior Fix: Never use raw HashMaps as caches. Always use Caffeine / Redis with strict eviction policies: Caffeine.newBuilder().maximumSize(10_000).expireAfterWrite(Duration.ofMinutes(10)).
Leak 2: Forgotten ThreadLocal Variables in Servlet Filters
public class TenantFilter extends OncePerRequestFilter {
    public static final ThreadLocal<SecurityContext> contextHolder = new ThreadLocal<>();

    @Override
    protected void doFilterInternal(HttpServletRequest req, HttpServletResponse res, FilterChain chain) {
        contextHolder.set(loadSecurityContext(req));
        chain.doFilter(req, res);
        // CRITICAL BUG: FORGOT contextHolder.remove() IN A FINALLY BLOCK!
        // Tomcat reuses threads in its pool -> the thread holds reference forever!
    }
}
Senior Fix: Always wrap ThreadLocal cleanups in a try ... finally { contextHolder.remove(); } block.

4 The Senior Interview Outage Script: Triage an OutOfMemoryError in Prod

When an interviewer asks: "Your Spring Boot pods in AWS are restarting every 4 hours with OutOfMemoryError. Walk me through your triage process step-by-step."

Step 1: Check if -XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=/dumps/heap.hprof is enabled. This instructs the JVM to automatically write the entire RAM state to disk at the exact moment of failure.
Step 2: Download the heap.hprof file and open it in Eclipse Memory Analyzer Tool (MAT) or IntelliJ Profiler.
Step 3: Open the Leak Suspects Report and look at the Dominator Tree. This groups memory by which single Object instance retains the highest percentage of heap.
Step 4: Trace the Incoming References to GC Roots. If it points to an unevicted static collection, a forgotten ThreadLocal, or a Hibernate query loading 2,000,000 unpaginated entities, deploy the specific hotfix immediately.
