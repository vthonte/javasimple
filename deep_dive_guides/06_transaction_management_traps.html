Spring @Transactional Pitfalls, Dynamic Proxies & Propagation Mechanics

Why @Transactional silently fails when methods are called internally within the same class (Self-Invocation), why Spring ignores Checked Exceptions by default, and how propagation levels (REQUIRES_NEW) work under the hood.

1 How @Transactional Actually Works: Dynamic CGLIB Proxies

Java does not natively have an @Transactional keyword in the language. Spring provides it using Aspect-Oriented Programming (AOP) via dynamic bytecode generation.

What Spring Actually Does When You Annotate a Class with @Transactional:

Spring does not inject your actual class instance into other beans. Instead, Spring generates a CGLIB Proxy subclass that wraps your real bean: 

// Conceptual code generated dynamically by Spring:
public class OrderService$$SpringCGLIBProxy extends OrderService {
    @Override
    public void createOrder(Order order) {
        TransactionStatus status = transactionManager.getTransaction(...);
        try {
            super.createOrder(order); // Calls your actual business code
            transactionManager.commit(status); // Commits if no error
        } catch (RuntimeException | Error ex) {
            transactionManager.rollback(status); // Rolls back
            throw ex;
        }
    }
}

2 Trap 1: The Self-Invocation Trap (Proxy Bypass)

The Bug Code:
@Service
public class OrderService {

    // Method A has NO @Transactional
    public void checkout() {
        // ... validating cart ...
        this.saveOrder(); // INTERNAL METHOD CALL!
    }

    // Method B HAS @Transactional
    @Transactional
    public void saveOrder() {
        orderRepo.save(...);
    }
}
Why this fails silently in production:
When another controller calls orderService.checkout(), it calls the Proxy. The Proxy sees that checkout() has no transaction annotation, so it does nothing and calls the real instance. Inside the real instance, this.saveOrder() calls the method directly on this (the raw object), bypassing the Proxy completely! No transaction is ever started.
The Senior Fix: Move saveOrder() to a separate dedicated OrderWriterService bean, or inject OrderService self-referentially via constructor/setter.

3 Trap 2: The Default Rollback Rule (Checked vs. Unchecked Exceptions)

Interviewers love asking: "An exception was thrown inside a @Transactional method, but the database changes were STILL committed! Why?"

Unchecked Exceptions (Rolls Back)

Subclasses of RuntimeException (e.g. NullPointerException, IllegalArgumentException, custom business exceptions extending RuntimeException). Spring rolls back by default.

Checked Exceptions (DOES NOT Roll Back!)

Direct subclasses of Exception (e.g. IOException, SQLException). Spring assumes you will handle these, so it COMMITS by default!

The Golden Senior Rule: In enterprise code, always specify rollback explicitly:
@Transactional(rollbackFor = Exception.class)

4 Transaction Propagation Levels Explained

Propagation If Transaction Exists If No Transaction Exists Real-World Use Case
REQUIRED (Default) Joins existing Creates new Standard business logic. All steps succeed or fail together.
REQUIRES_NEW Suspends existing; creates brand new Creates new Audit logs & security alerts that MUST save even if the main transaction fails and rolls back.
MANDATORY Joins existing Throws Exception! Methods that must never be called outside a parent transaction.
NEVER Throws Exception! Executes non-transactionally Operations that must not hold locks or connection resources.
