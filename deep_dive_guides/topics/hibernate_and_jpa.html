Hibernate & JPA: Persistence Context & Automatic Dirty Checking

How ORM really manages entity state: The 4 Entity States (Transient, Managed, Detached, Removed), First-Level Cache (Session), Flush vs Commit, and the Dirty Checking snapshot algorithm.

💡

ELI5: The Hotel Front Desk & Room Key (The Persistence Context)

In Node/Prisma, when you update a user, you must explicitly call prisma.user.update({ where: { id }, data: { email } }).

In Hibernate, when you load an entity from the database, the Hotel Front Desk (EntityManager / Persistence Context) checks the entity into a room and takes an exact photographic snapshot of it in the First-Level Cache. If you later write user.setEmail("new@email.com"), you DO NOT CALL .save()! At the end of the transaction, Hibernate compares the object with the snapshot, spots the difference, and automatically fires the SQL UPDATE statement!

📊 The 4 JPA Entity States

1. Transient

Created via new User(). No DB row, no ID, not tracked.

2. Managed

Tracked by EntityManager. Changes auto-synced to DB upon flush.

3. Detached

Has DB identity, but session closed. Modifying does NOT update DB!

4. Removed

Marked for deletion. Emits SQL DELETE on flush.

Automatic Dirty Checking in Code

@Transactional
public void updateUserName(Long userId, String newName) {
    // 1. Fetches from DB -> entity enters MANAGED state in First-Level Cache
    User user = userRepository.findById(userId)
        .orElseThrow(() -> new EntityNotFoundException());

    // 2. Modify field in memory:
    user.setName(newName);

    // 3. NOTICE: We DO NOT call userRepository.save(user)!
    // When the @Transactional method exits:
    // Hibernate compares current object with original snapshot ->
    // Generates: UPDATE users SET name = ? WHERE id = ?
}
