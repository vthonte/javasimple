Collections Internals: HashMap Hashing, Treeification & ConcurrentHashMap

How HashMap works under the hood: bucket arrays, index calculation with bitwise AND, handling hash collisions, Java 8 Red-Black Tree treeification, and ConcurrentHashMap segment-less CAS locking.

💡

ELI5: The 16 Mailboxes (How HashMap Finds Your Mail)

A HashMap starts with 16 mailboxes (an array of size 16). When you insert a key, Java calculates the key's hashCode() (like a fingerprint number) and uses modulo math to pick mailbox number 0 to 15.

If two different keys land in the exact same mailbox (a hash collision), old Java chained them in a linked list. If a bad actor spammed 10,000 keys into 1 mailbox, lookup slowed down from \(O(1)\) to \(O(N)\) (DoS vulnerability).

The Java 8 Breakthrough (Treeification): When any single bucket gets more than 8 items (`TREEIFY_THRESHOLD = 8`), Java transforms the linked list into a self-balancing Red-Black Tree, ensuring performance never drops below \(O(\log N)\)!

📊 HashMap Bucket Index Calculation

1. Calculate Hash: int h = key.hashCode();
2. Bit-Spread (reduces collisions): int hash = h ^ (h >>> 16);
3. Bucket Index (Fast bitwise AND equivalent to modulo): index = (n - 1) & hash;

Senior Interview Bar: The hashCode() & equals() Contract

The Silent Bug: Overriding equals() without hashCode()

If two objects are considered equal by equals(), they MUST have the exact same hashCode()! If you forget to override hashCode(), two equal objects get different bucket indexes, meaning map.get(key) will return null even when the key is right in the map!

💡 Senior Fix: In Modern Java 16+, use record which auto-generates perfectly compliant equals() and hashCode() implementations for you!
