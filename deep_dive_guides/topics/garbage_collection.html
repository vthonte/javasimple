Modern Garbage Collection: G1GC vs. ZGC vs. Shenandoah

How the JVM eliminated Stop-The-World (STW) pauses: Tri-color marking, colored pointers, load barriers, and choosing the right GC for ultra-low latency APIs.

💡

ELI5: The Cleaning Crew While the Office is Open

In old Java (Java 7 and earlier), when memory was full, the JVM locked the doors and blew a whistle: "Stop the World!". All HTTP requests froze for 2 to 10 seconds while the janitor swept the floors. Clients timed out and 504 errors erupted.

Modern ZGC (Java 21) cleans the office while people are actively working at their desks. It uses "colored pointers" and "load barriers" so the cleaning pause is under 1 millisecond, even on giant 16 Terabyte heaps!

📊 GC Algorithm Architectural Comparison

GC Algorithm Default In Typical Pause Time Heap Size Target Best Use Case
G1GC (Garbage-First) Java 9 - 21+ (Default) 10ms – 100ms 4GB – 64GB General purpose web apps balancing throughput and latency.
Generational ZGC Java 21+ (-XX:+UseZGC) < 1 millisecond 16GB – 16TB Ultra-low latency APIs, trading apps, high-throughput microservices.
Shenandoah Red Hat JDK / OpenJDK < 10ms 8GB – 100GB Concurrent compaction using Brooks pointers without colored pointers.

Enabling Generational ZGC in Docker Containers

# Run Java 21 with sub-millisecond GC pauses:
java -XX:+UseZGC -XX:+ZGenerational \
     -Xms4g -Xmx4g \
     -XX:+AlwaysPreTouch \
     -jar app.jar

-XX:+AlwaysPreTouch forces the OS to allocate all physical RAM pages at startup so the JVM never pauses during runtime requests!
