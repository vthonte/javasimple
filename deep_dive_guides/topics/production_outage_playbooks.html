Live Production Incident Playbooks: 100% CPU, Deadlocks & HikariCP Depletion

Battle-tested terminal commands and diagnostic sequences used by Senior Site Reliability Engineers (SREs) during live P1/P0 outages on Kubernetes pods.

🔥 Playbook 1: 100% CPU Infinite Loop on Linux Pod

Severity: P0

Run these 3 commands inside the Kubernetes container terminal to find the exact class and line number causing the loop: 

# Step 1: Find the exact thread burning CPU (shows Thread ID under PID column)
top -H -p <JVM_PID>
# Suppose Thread ID is 4591

# Step 2: Convert the decimal TID to Hexadecimal (JVM thread dump uses Hex nid)
printf "%x\n" 4591
# Output: 0x11ef

# Step 3: Grep jstack for that exact hex nid:
jstack <JVM_PID> | grep -A 25 0x11ef
"http-nio-8080-exec-4" #42 daemon prio=5 tid=0x00007f nid=0x11ef runnable [0x00007f]
    java.lang.Thread.State: RUNNABLE
        at com.example.service.OrderService.calculateDiscount(OrderService.java:142) <-- ROOT CAUSE!

🚰 Playbook 2: Connection Pool Exhaustion (HikariCP Timeout)

Severity: P1

Error in logs: Connection is not available, request timed out after 30000ms (HikariPool-1 - Connection timeout). All threads are stuck waiting for a database socket.

How to detect connection leaks in 1 minute:

Add the leak detection threshold in application.yml:

spring:
  datasource:
    hikari:
      maximum-pool-size: 20
      connection-timeout: 30000
      leak-detection-threshold: 5000 # Logs warning with stack trace if connection held > 5s!

HikariCP will print: "Apparent connection leak detected at com.example.service.ReportService.generateReport() (unclosed connection)".

🔒 Playbook 3: Thread Deadlock Freeze

Severity: P0

When threads lock each other, run JDK's built-in deadlock analyzer: 

# Run jcmd to analyze thread locks:
jcmd <JVM_PID> Thread.print
Found one Java-level deadlock:
"Thread-1" waiting to lock Monitor A (held by "Thread-2")
"Thread-2" waiting to lock Monitor B (held by "Thread-1")
