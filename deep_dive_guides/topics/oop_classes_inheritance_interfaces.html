Core OOP in Java: Classes, Inheritance, Interfaces & Polymorphism

Building your object-oriented mental model: Encapsulation (access modifiers), Inheritance (extends & super), Abstraction (Abstract Classes vs Interfaces), and Runtime Polymorphism (Method Overriding vs Overloading).

ELI5: The Blueprint, The Family Tree, and The USB Port

1. Class vs Object (Blueprint vs Car)

A class Car is just an architectural drawing. When you type new Car(), physical steel is stamped and a real object drives off the assembly line into memory.

2. Inheritance (DNA Inheritance)

class ElectricCar extends Car. ElectricCar inherits engine starts and steering from its parent, but overrides fueling to use a battery charger.

3. Interface (The USB Port Contract)

A USB interface doesn't care if you plug in a mouse, keyboard, or flash drive. Any device that implements the standard USB pins works seamlessly!

1. Inheritance & Method Overriding (@Override)

// Parent Base Class
public class PaymentGateway {
    protected final String merchantId; // protected = accessible to subclasses

    public PaymentGateway(String merchantId) {
        this.merchantId = merchantId;
    }

    public void processPayment(double amount) {
        System.out.println("Processing generic transaction of $" + amount);
    }
}

// Subclass inherits via 'extends'
public class StripeGateway extends PaymentGateway {

    public StripeGateway(String merchantId) {
        super(merchantId); // Calls parent constructor!
    }

    // Runtime Polymorphism: Overriding parent behavior
    @Override
    public void processPayment(double amount) {
        System.out.println("Charging $" + amount + " via Stripe API for " + merchantId);
    }
}

2. Interfaces: The Universal Contract

Clean Architecture Foundation

In Java, a class can only extend 1 single parent class (no multiple inheritance diamond problem). But a class can implement unlimited interfaces! 

// The Interface: Defines WHAT must be done, not HOW.
public interface NotificationService {
    void sendNotification(String to, String message);

    // Java 8+ Default Methods: Optional default implementation!
    default boolean isUrgent() {
        return false;
    }
}

// Implementation 1: Email
@Service
public class EmailNotificationService implements NotificationService {
    @Override
    public void sendNotification(String to, String message) {
        System.out.println("Sending SMTP Email to " + to + ": " + message);
    }
}

// Implementation 2: SMS
@Service
public class SmsNotificationService implements NotificationService {
    @Override
    public void sendNotification(String to, String message) {
        System.out.println("Sending Twilio SMS to " + to + ": " + message);
    }
}
💡 Why this matters for Spring Boot:

Your Controller depends on the interface NotificationService, NOT the concrete class! During tests, you can easily swap in a mock without changing your controller code. This is the Dependency Inversion Principle (DIP) in SOLID design.

Abstract Class vs Interface: When to Use Which?

Abstract Class (is-a)

• Used when classes share state (instance fields) and constructors.
• A class can only extend ONE abstract class.
• Example: BaseEntity with id, createdAt, updatedAt fields inherited by all database models.

Interface (can-do)

• Pure behavioral contract (no state, no mutable fields).
• A class can implement MULTIPLE interfaces.
• Example: Serializable, Comparable, Runnable, EventListener.
