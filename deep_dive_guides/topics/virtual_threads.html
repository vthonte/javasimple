Everything you need to know from the ground up: why OS threads were a bottleneck, how Virtual Threads work at the JVM level, carrier threads, continuation unmounting, and the "pinning" trap.

ELI5: Real Actors vs Script Roles

In traditional Java, if a script has 10,000 characters, you had to hire 10,000 real human actors (OS Threads). Each actor costs \$1,000/day and takes physical space. If 9,990 actors are just waiting off-stage (waiting on DB queries or network calls), you go bankrupt from payroll.

Virtual Threads are the script pages. You hire only 8 real actors (Carrier Threads matching your CPU cores). An actor picks up a page, speaks the line, and if the script says "Wait 3 seconds for response", the actor drops the page and immediately acts out someone else's line! When the response arrives, any available actor picks up the page and continues.

Code Examples: How to Use Virtual Threads

Level 1: Beginner

Starting a Virtual Thread

// 1. Using Thread.startVirtualThread()
Thread.startVirtualThread(() -> {
    System.out.println("Running on: " + Thread.currentThread());
});

// 2. Using Thread.ofVirtual() builder
Thread vThread = Thread.ofVirtual()
    .name("order-worker-", 1)
    .start(() -> {
        // Safe to call blocking methods like Thread.sleep or DB queries!
        try { Thread.sleep(1000); } catch (InterruptedException e) {}
    });
Level 2: Spring Boot Integration

Enabling Virtual Threads in Spring Boot 3.2+

In Spring Boot 3.2+, you do not need to rewrite your controllers. You enable it with 1 line of configuration:

# In application.properties:
spring.threads.virtual.enabled=true

Now Tomcat uses a Virtual Thread for every incoming HTTP request instead of the standard 200 platform thread pool!

Level 3: Pro / Production Caveat Senior Interview Bar

The "Thread Pinning" Trap (synchronized blocks)

If a virtual thread executes a blocking I/O operation inside a synchronized block or a native C method (JNI), the virtual thread pins the underlying carrier thread! The carrier thread is trapped and cannot serve other requests.

❌ Pinned (Blocks Carrier)
public synchronized String fetch() {
  // Blocking I/O inside synchronized pins!
  return restTemplate.getForObject(...);
}
✅ Safe Fix (ReentrantLock)
private final ReentrantLock lock = new ReentrantLock();

public String fetch() {
  lock.lock();
  try {
    return restTemplate.getForObject(...); // Unmounts safely!
  } finally {
    lock.unlock();
  }
}

How to detect in production: Run with JVM flag: -Djdk.tracePinnedThreads=full
