The N+1 Query Trap: Detection, JOIN FETCH, and In-Memory Pagination Dangers

Why default Lazy Loading crashes production databases: how 1 query multiplies into 1,000 queries, comparing JOIN FETCH vs @EntityGraph vs Batch Fetching, and the terrifying in-memory pagination warning (HHH000104).

The 3 Senior Solutions to N+1

Solution 1: JPQL JOIN FETCH 
public interface UserRepository extends JpaRepository<User, Long> {
    // Overrides lazy loading and fetches Orders in 1 single SQL JOIN!
    @Query("SELECT u FROM User u JOIN FETCH u.orders")
    List<User> findAllWithOrders();
}
Solution 2: @EntityGraph (Clean Declarative) 
public interface UserRepository extends JpaRepository<User, Long> {
    // Declarative query without writing raw JPQL string!
    @EntityGraph(attributePaths = {"orders"})
    List<User> findAll();
}
Solution 3: Global Batch Size (IN Clause) 
# In application.properties:
# Replaces N queries with: SELECT * FROM orders WHERE user_id IN (?, ?, ..., ?)
spring.jpa.properties.hibernate.default_batch_fetch_size=50

Senior Architecture Trap: In-Memory Pagination (HHH000104)

❌ NEVER use JOIN FETCH on a @OneToMany relationship with Pageable!

If you write: @Query("SELECT u FROM User u JOIN FETCH u.orders") Page<User> findAll(Pageable p), SQL returns duplicate user rows due to the join. SQL cannot limit the parent rows accurately.

Hibernate logs: "HHH000104: firstResult/maxResults specified with collection fetch; applying in memory!"

Catastrophe: Hibernate downloads ALL 5,000,000 users into JVM Heap RAM and performs pagination in memory, instantly crashing your server with an OutOfMemoryError!

✅ Senior Fix: Paginate ONLY the parent entity ID first without join fetch, then use default_batch_fetch_size or a separate query to fetch children for that specific page of 20 IDs!
