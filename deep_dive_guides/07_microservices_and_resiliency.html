ELI5: The "Dual-Write" Ghost Order Nightmare

Beginner Mental Model
The Problem: Writing to DB AND Kafka

You save an Order into PostgreSQL, and then send a message to Kafka: kafka.send("order-created"). What happens if Kafka is down or network drops? The DB committed the order, but Kafka never got notified! Or what if Kafka sends the message, but the DB crashes during commit? Ghost payments happen!

The Senior Fix: Transactional Outbox Pattern

Instead of calling Kafka directly, you write the event into an outbox_table in the SAME database transaction as your order! Since it's inside 1 Postgres transaction, it is 100% atomic. A background engine (like Debezium CDC) streams rows from the outbox table to Kafka reliably.

1 The Dual-Write Problem: Why You Cannot Just Call Kafka in a Transaction

The Naive Code Pattern Found in Inexperienced Codebases:
@Transactional
public void placeOrder(Order order) {
    orderRepository.save(order); // Step 1: Write to PostgreSQL
    kafkaTemplate.send("order-created", order); // Step 2: Publish to Kafka
    // CRITICAL DUAL-WRITE FLAW:
    // What if Kafka is unreachable? DB rolls back, but maybe message was sent.
    // What if DB commit fails after Kafka sends? Ghost event sent to consumers!
}

PostgreSQL and Kafka are two separate distributed systems without a shared distributed transaction coordinator (2PC is too slow and creates lock deadlocks).

2 The Industry Standard Solution: Transactional Outbox Pattern

Instead of publishing to Kafka directly inside the HTTP request, write the event into an OUTBOX table in the exact same relational database transaction! 

@Transactional
public void placeOrder(Order order) {
    orderRepository.save(order); // 1. Save business entity

    // 2. Save event payload into outbox table in SAME ACID transaction!
    OutboxEvent event = new OutboxEvent("ORDER_CREATED", toJson(order));
    outboxRepository.save(event);
    // Guaranteed atomic! Both succeed or both rollback.
}
How the Message Gets to Kafka:

A separate background process reads from the Outbox table and publishes to Kafka. The best practice is using Change Data Capture (CDC) via Debezium, which tails the PostgreSQL Write-Ahead Log (WAL) directly with near-zero latency, guaranteeing at-least-once delivery without polling overhead!

3 Distributed Consistency: The Saga Pattern

Choreography-based Saga

Each service acts independently and listens to domain events from Kafka.

Order Service emits OrderCreated → Payment Service listens and charges card, emits PaymentSuccess → Inventory Service listens and reserves stock.

Pros: Simple, decoupled.
Cons: Hard to debug when 8+ services are involved; cyclic dependencies.

Orchestration-based Saga (Recommended at Scale)

A centralized Saga Orchestrator (e.g. Temporal, Camunda, or a custom state machine service) directs all steps:

"OrderOrchestrator calls Payment âž” calls Inventory âž” confirms Order".

If Inventory fails: Orchestrator explicitly invokes refundPayment() compensating transaction. State is visible in one place.

4 Resiliency: Circuit Breakers (Resilience4j vs Node Opossum)

If your Recommendation Microservice slows down from 20ms to 8,000ms, your main thread pool will back up and crash the whole application. 

@Service
public class PaymentGatewayClient {

    @CircuitBreaker(name = "stripeBreaker", fallbackMethod = "fallbackCharge")
    @Retry(name = "stripeBreaker")
    @TimeLimiter(name = "stripeBreaker") // 2 second timeout
    public PaymentResponse process(PaymentRequest req) {
        return restClient.post().uri("/charges").body(req).retrieve().body(PaymentResponse.class);
    }

    // Fallback executes when Circuit is OPEN or times out:
    public PaymentResponse fallbackCharge(PaymentRequest req, Throwable t) {
        log.warn("Payment service unavailable, queuing for async retry: {}", t.getMessage());
        return new PaymentResponse("QUEUED_FOR_OFFLINE_PROCESSING");
    }
}
