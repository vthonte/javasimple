Module 02

Core Java Concurrency, Memory & Virtual Threads

Critical Senior Interview Topic
Why Interviewers Test Concurrency Thoroughly: In Node.js, you rarely worry about race conditions or shared mutable state in memory because code runs on a single thread. In Java, multiple threads execute the same code simultaneously. If two threads modify the same object, memory corruption or deadlock occurs unless you understand locks, memory models, and atomicity.

⚙️ The 3 Concurrency Models Compared

1. Node.js Event Loop Model

1 main thread. Non-blocking I/O callbacks queued in libuv. CPU-heavy loops block ALL incoming requests for everyone.

2. Traditional Java (ThreadPool / Tomcat)

Platform OS Threads (1 thread = ~1MB stack memory). Typically limited to 200–1,000 threads. When waiting for DB or Redis, thread sits idle blocking OS memory.

3. Modern Java 21 (Virtual Threads / Project Loom)

Millions of lightweight threads managed by the JVM (bytes each). When a Virtual Thread does blocking I/O, JVM unmounts it from the carrier OS thread. Best of both worlds: simple synchronous code with Node.js async scale!

How to enable Virtual Threads in Spring Boot 3/4:
spring.threads.virtual.enabled=true

That's it! Tomcat immediately shifts from 200 OS threads to unbounded virtual threads per HTTP request.

🔒 Handling Shared State (Race Conditions)

In Node.js, count++ is safe because JavaScript is single-threaded. In Java, multiple HTTP requests hit the same singleton controller simultaneously!

❌ Thread Unsafe (Race Condition Bug) 
@Service
public class OrderCounterService {
    private int counter = 0; // Shared mutable state!

    public void increment() {
        counter++; // NOT atomic! Reads, increments, writes.
                   // 2 threads collide -> data loss!
    }
}
✅ Thread Safe (Modern Atomic / Locks) 
@Service
public class OrderCounterService {
    // Option A: Lock-free CPU CAS (Compare-And-Swap) - FASTEST
    private final AtomicInteger counter = new AtomicInteger(0);

    public int increment() {
        return counter.incrementAndGet(); // Thread safe!
    }

    // Option B: ReentrantLock / Synchronized for multi-step blocks
    private final ReentrantLock lock = new ReentrantLock();
    public void processCritical() {
        lock.lock();
        try { /* safe multi-step update */ }
        finally { lock.unlock(); }
    }
}

🧠 JVM Memory Architecture vs V8 Engine (Node.js)

1. Stack Memory

Each thread has its private Stack. Stores primitive local variables and references to objects. Fast, allocated and cleared automatically when methods return. Overflow causes StackOverflowError.

2. Heap Memory

Shared by all threads. Stores all new Object() instances. Managed by the Garbage Collector (Young Gen / Eden, Survivor, Old Gen). Exhaustion causes OutOfMemoryError: Java heap space.

3. Metaspace

Stores class definitions, bytecode, and method metadata in native OS memory (not heap). Replaced PermGen in Java 8. Grows automatically based on OS RAM.

Collections Framework & Streams (vs JS Array methods)

Everyday Coding
Java Collection JS / Node Equivalent Time Complexity Thread Safe? When to use in Backend
ArrayList<T> Array [] O(1) get, O(N) insert/del No Default list. High-speed index lookup. Fast appends.
LinkedList<T> Rare in JS O(N) get, O(1) head/tail No Frequent insertions/deletions at start or middle. Queue/Deque.
HashMap<K,V> Object / Map O(1) average lookup No Standard key-value dictionary within a single method/thread.
ConcurrentHashMap<K,V> N/A (Single-threaded) O(1) lock-free read Yes (Segment locks) In-memory caches accessed by multiple threads/HTTP requests.
HashSet<T> Set O(1) contains No Deduplication, checking uniqueness of IDs or emails.
JavaScript (Node.js) Functional Pipeline Eager 
// Eager evaluation: creates intermediate arrays in memory
const activeUsers = users
  .filter(user => user.isActive)
  .map(user => user.email.toLowerCase())
  .slice(0, 10);

JS array methods execute immediately and allocate a brand new array after every .filter() and .map().

Java 8+ Stream Pipeline Lazy & Optional Multi-Core 
// Lazy evaluation: no work done until terminal operator (.toList())
List<String> activeUsers = users.stream()
  .filter(User::isActive)              // Method reference
  .map(user -> user.getEmail().toLowerCase())
  .limit(10)
  .toList();                          // Terminal operator

// Bonus: Instant multi-core parallel processing!
users.parallelStream().filter(...).toList();

Streams are lazy. Elements are pulled one at a time only when needed. Intermediate steps allocate zero arrays!

Module 05

JPA, Hibernate & The Deadly N+1 Query Trap

#1 Performance Bottleneck

The N+1 Query Problem in Action

Simulated Users:
❌ Naive Query (N+1 Hazard) 51 SQL Queries! 
// 1. Fetches all users (1 query)
List<User> users = userRepository.findAll();

// 2. Accessing orders triggers 1 query PER user! (N queries)
for (User user : users) {
    System.out.println(user.getOrders().size());
}
Total DB queries sent: 1 + 50 = 51 queries! At scale, this exhausts your database connection pool instantly.
✅ Senior Solution: JOIN FETCH or @EntityGraph 1 Single SQL Query! 
public interface UserRepository extends JpaRepository<User, Long> {
    // Solves N+1 in 1 clean SQL JOIN query!
    @Query("SELECT u FROM User u LEFT JOIN FETCH u.orders")
    List<User> findAllWithOrders();
}
Generated SQL: SELECT * FROM users u LEFT JOIN orders o ON u.id = o.user_id. Total queries: Always 1 regardless of user count!
Module 06

Spring @Transactional Traps & Propagation

Data Integrity
Trap 1: Self-Invocation (Proxy Bypass)
@Service
public class OrderService {

    public void checkout() {
        // CALLING INTERNAL METHOD DIRECTLY!
        // Spring AOP Proxy is bypassed! @Transactional is IGNORED!
        this.saveOrder(); 
    }

    @Transactional
    public void saveOrder() {
        orderRepo.save(...);
    }
}

Why it fails: Spring's @Transactional works by wrapping your bean in a dynamic CGLIB Proxy. When method A calls method B inside the same class using this.saveOrder(), it calls the raw Java instance, bypassing Spring's proxy interceptor entirely!

Fix: Move saveOrder() to a separate service bean, or inject OrderService into itself.
Trap 2: Default Rollback on Checked Exceptions
@Transactional
public void processPayment() throws Exception {
    paymentRepo.deductBalance();
    
    // Throws a CHECKED Exception (subclass of Exception, not RuntimeException)
    if (externalGatewayFailed()) {
        throw new Exception("Payment gateway timed out"); 
        // BY DEFAULT: SPRING DOES NOT ROLLBACK ON CHECKED EXCEPTIONS!
    }
}

Why it fails: By default, Spring only rolls back on unchecked exceptions (RuntimeException and Error).

Fix: Always write @Transactional(rollbackFor = Exception.class) to guarantee rollbacks on all exceptions.
Module 07

Microservices, Distributed Consistency & Resiliency

System Design (4-7 Yrs)

💳 Distributed Transactions (Why 2PC Fails)

The Saga Pattern (Choreography vs Orchestration)

A sequence of local transactions. Each service updates its DB and publishes an event (via Kafka/RabbitMQ). If step 3 fails, compensating transactions are triggered backwards to refund inventory and cancel order.

Transactional Outbox Pattern

Solves the dual-write problem: writing to DB and publishing to Kafka cannot be atomic. Save message into an OUTBOX database table in the same DB transaction! Debezium (CDC) or a worker pushes to Kafka reliably.

⚡ Resiliency Patterns (Resilience4j)

Circuit Breaker States:
CLOSED → OPEN → HALF-OPEN 
@CircuitBreaker(name = "paymentService", fallbackMethod = "paymentFallback")
@Retry(name = "paymentService")
public PaymentResponse charge(PaymentRequest req) {
    return restTemplate.postForObject(url, req, PaymentResponse.class);
}

// Fallback method executes when circuit trips:
public PaymentResponse paymentFallback(PaymentRequest req, Throwable t) {
    return new PaymentResponse("PENDING_OFFLINE_REVIEW");
}

Module 09

Interactive Code Review & Flaw Detection Challenge

Hands-on Practice

Spot the 3 Critical Senior Flaws in this Spring Service:

@RestController
public class OrderController {

    @Autowired // Flaw 1: ?
    private OrderRepository orderRepo;

    private int requestCounter = 0; // Flaw 2: ?

    @GetMapping("/orders/user/{id}")
    @Transactional // Flaw 3: ?
    public List<OrderDTO> getOrders(@PathVariable Long id) {
        requestCounter++;
        List<Order> orders = orderRepo.findAllByUserId(id);
        // Triggers N+1 query when mapped to DTO:
        return orders.stream()
            .map(o -> new OrderDTO(o.getId(), o.getItems().size())) 
            .toList();
    }
}
Flaw 1 (Architecture): Direct field injection of Repository into Controller skips Service boundary and makes testing difficult. Fix: Inject Service layer via constructor.
Flaw 2 (Concurrency): Controllers are singletons shared across thousands of concurrent threads. requestCounter++ is non-atomic and causes race conditions. Fix: Use AtomicInteger or Micrometer Counter metric.
Flaw 3 (Database Performance): Calling o.getItems().size() inside stream triggers N+1 SQL queries across the network! Furthermore, placing @Transactional on a GET endpoint keeps a database connection checked out for the entire HTTP serialization. Fix: Use JOIN FETCH in repository and use read-only transactions at the Service layer.

Senior Behavioral, Client & Stakeholder Articulation

The 4-7 Yrs Leadership Bar

1. "When should we choose Java over Node.js (or vice-versa)?"

How to articulate: "Node.js excels in fast prototyping, I/O-heavy BFF (Backend-for-Frontend) layers, and real-time WebSockets where development velocity and single-language full-stack JavaScript are priorities. Java and Spring Boot excel in complex enterprise domains requiring strict domain-driven design, multi-threaded CPU computational tasks, strict static type safety at scale, and bulletproof transaction management."

2. "How do you handle ambiguous client requirements?"

How to articulate: "I never write code against assumptions. I schedule a brief 15-minute alignment with product/client stakeholders using visual sequence diagrams and concrete edge-case user stories. I document non-functional requirements early (latency SLAs, peak RPS, data retention, consistency trade-offs) so engineering and business share the same success criteria."

3. "How do you negotiate technical debt with Product Managers?"

How to articulate: "I frame tech debt in business terms, not engineering purity. Instead of saying 'we need to rewrite this query,' I explain: 'Optimizing this N+1 query reduces our AWS RDS database bill by 35% and cuts p99 checkout latency from 800ms to 90ms, directly impacting cart conversion.' I allocate 15-20% of every sprint capacity to technical hygiene."

4. "Agile / SAFe / Sprint Planning Experience"

How to articulate: "I participate actively in backlog refinement, story pointing with Planning Poker, and breaking large epic features into vertical slices that deliver testable user value every sprint. In retrospectives, I focus on blameless root-cause analysis for any missed sprint commitments or production defects."
